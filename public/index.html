    Start composing →ComposePipeline →
    Container tooling. A whole operating system.
    Start with a bootc base containing the kernel and userspace. Define your OS in a Containerfile, publish it to a registry, then install it on a VM or physical host. Unlike an application container, it keeps the base's startup and user defaults.
    Compose→Build→Publish→Boot→Update
    

    Imagecraft writes recipes; it never executes them.
    

    Tip · Start small
    Choose a starter, add your packages, then review the generated Containerfile. Commands run during the build; enabled services start when the installed OS boots.
    

    Warning · Keep secrets outside the image
    Never put credentials in commands, ARG, ENV, LABEL or selected files. Image layers and exported recipes can expose them; deleting a file in a later layer does not securely remove it. Secret checks are incomplete.
    

    Info · OS rollback is not data recovery
    Rollback does not restore /var or undo schema migrations. Test upgrade and rollback with representative data, and rehearse restoring backups.
    

    Instructions and builder stages
    Packages and commands become build-time RUN instructions. Install software before commands that need it. Services enable systemd units in the final OS to start at boot; they do not start services during the build.
    LABEL is public image metadata. ARG is a stage-scoped build option: declare it in every stage that needs it. ENV persists in that image stage and influences later commands; it is not a guarantee of a systemd service's runtime environment. WORKDIR sets/creates the directory for later instructions in its stage; it does not set the OS boot behavior.
    Add named builders in Compose's options, assign their rows, then order builders before the final OS. Artifact COPY can copy a file only from an earlier builder. Only explicitly copied artifacts enter the final OS; builder ARG, ENV and WORKDIR settings do not transfer. Match the target architecture and RHEL ABI (including linked libraries) and review each builder base independently. Pinning the final OS does not pin builders or package versions.
    

    

    Local files, permissions and portable recipes
    Ordered COPY steps include a selected local regular file, a safe files/ source path, an explicit absolute destination file path and octal permissions (for example 0644 for configuration or 0755 for an executable). Unlike ADD, COPY does not implicitly download or extract archives. Ownership, service access and SELinux contexts still need review: chmod alone does not set a correct SELinux label. Test access under enforcing SELinux on the installed RHEL system; do not disable SELinux to make a recipe pass.
    Export the complete build folder (.tar) to include the Containerfile, referenced files, allowlist .containerignore/.dockerignore rules and selected provider YAML. Extract into a new empty folder, inspect everything, and build from that folder or commit it at the repository root. A standalone Containerfile download does not include COPY inputs.
    

    Portability is explicit, not a backup service
    Recipe text and preferences are saved in this browser; file bytes stay in memory only. Reloading requires file reselection. Portable JSON includes referenced file bytes as base64 and can move a recipe between browsers after review. Limits: 5 MiB per file, 20 MiB total file bytes, 30 MiB JSON import, 100 steps and 10 builders. The versioned format is imagecraft-recipe, schema version 2; unsupported versions are rejected. Neither export encrypts its contents.
    

    

    Configuration, persistent state and base updates
    Configuration is not persistent application data
    /etc contains system configuration; image defaults and local administrator changes participate in bootc's configuration merge behavior. Test conflicts when an update changes a locally modified file. /var holds persistent runtime state shared across deployments. Do not assume files baked under /var will replace existing databases, logs or application data during upgrades. Plan initialization, migrations, backups and restore separately.
    An OS rollback switches the deployment; it does not roll back application data. A newer application may migrate data that the previous version cannot read. Test both upgrade and rollback against representative state and rehearse restoring backups.
    

    Review immutable bases, then test deliberate updates
    Compose can apply a manually reviewed sha256 base digest. Inspect the candidate on your own authenticated host, verify its architecture and provenance, record the old digest, then apply the pin explicitly. It never refreshes automatically and changing RHEL version clears it. A digest fixes the base reference, not entitlement, package repositories, builder outputs or overall reproducibility. Rebuild and boot-test each candidate before promotion; keep the previous known-good image digest and a data recovery plan.
    

    

    Credentials, check limits and further reading
    Keep passwords, tokens, private keys and registry authentication out of portable recipes and committed build folders. Use your CI provider's secret store and provision machine-specific runtime secrets on the target, outside the image. Review every instruction and file byte, including imports: credential and path filters are heuristics, not comprehensive detection. Imagecraft neither accepts build credentials nor executes recipes.
    All six starters are illustrative, not production-validated appliances. Local checks do not verify package availability, shell correctness, entitlement, successful builds or bootability. Automated accessibility checks do not establish WCAG compliance or replace screen-reader and user feedback.

    Initial-user config · config.toml
    Save beside the downloaded script in a new working directory. Review all placeholders first; the script creates a new output directory and refuses to reuse one.
    

    vSphere import · not an OVA deployment
    1. Verify the generated VMDK signature before uploading it to an isolated datastore. Retain the original file and its bundle.
    2. Create a new destination directory, then clone the uploaded disk with the ESXi shell command below. Replace both datastore paths; never point at an existing VM disk. This example is for a conventional datastore, not a vSAN-specific workflow.
    3. Create a new x86_64 VM in vSphere and attach the cloned existing disk. Match its firmware, disk controller and guest compatibility to the tested RHEL image and your vSphere release; VMDK alone does not include VM settings or prove bootability.
    4. Boot-test networking, SSH, storage, services and SELinux before promotion. Conversion changes disk bytes: sign and verify each final distributed descriptor/extent file separately if shipping the converted result.

    Artifact formats, builder versions and provisioning limits
    QCOW2 is for a compatible QEMU/KVM VM. Raw contains an entire disk, not a filesystem or a safe file to copy over a running disk; choose and verify any hardware target separately. vSphere uses a VMDK plus reviewed VM settings, not an invented OVA export. No installer ISO is generated.
    These are RHEL 9/10 bootc-image-builder compatibility commands. Native architecture must match the host, builder and source image. The displayed legacy output path can differ with a newer builder; verify the actual file before signing/import. Disk layout, size, root filesystem and hypervisor requirements need release-specific review. They are not inferred from the recipe.

    Warning · Lint is not a boot test
    Before rollout, boot a disposable VM. Verify users, services, networking, firewall rules and enforcing SELinux access. Retain build logs, an immutable image digest and a tested previous deployment.
    

    Update an installed host
    1. Boot-test the published candidate in staging. Back up application data and retain the previous known-good digest.
    2. bootc status distinguishes the booted, staged and rollback deployments. upgrade stages the newest image at the current tracked target; it does not change the running OS. A fixed digest has no newer content to discover.
    3. Inspect the staged deployment, then reboot explicitly in a maintenance window. Check the booted digest and application health afterward. These examples avoid --apply, which can reboot automatically.
    

    Installed host · Update
    sudo bootc status
sudo bootc upgrade
sudo bootc status
# Activate only after inspecting the staged deployment, in a maintenance window:
sudo systemctl reboot
# After reconnecting, inspect the booted deployment and service health:
sudo bootc status
    

    Switch the tracked target · deliberate release promotion
    To promote a different repository, tag or immutable release, bootc switch stages that target for the next boot. Replace the digest placeholder with the candidate's verified published OS digest, not the Containerfile base pin. Future upgrade calls against a pinned digest are a no-op; promote the next digest deliberately. Provision target-host registry authentication outside the image; builder-host login is not transferred to installed hosts.
    Installed host · target change · review trust policy first
    Check the installed RHEL bootc version's target-change and signature-policy requirements first. See bootc switch ↗ and bootc upgrade ↗.
    

    Roll back if needed
    Rollback needs an available previous deployment, discards a staged update and selects the previous OS for the next boot. Inspect before rebooting, then verify the active digest and service health. Coordinate automatic update agents so they do not immediately undo your rollback.
    

    Warning · Rollback does not restore data
    It does not restore /var or undo schema migrations. Back up data and test application compatibility with both deployments before rollout.
    

    Installed host · Rollback
    sudo bootc status
sudo bootc rollback
sudo bootc status
# Activate only after inspecting the deployment, in a maintenance window:
sudo systemctl reboot
# After reconnecting, inspect the booted deployment and service health:
sudo bootc status
    

    Rollback and local configuration
    /var remains persistent across OS deployments, including database migrations. Rollback also reuses the prior deployment's /etc; recent local configuration changes do not automatically follow it. Test both application and configuration compatibility and maintain separate data backups.

    Sign and verify the release
    Use an already provisioned signing key and an independently trusted public key. These examples only generate commands: Imagecraft never handles private keys, signs files or publishes signatures. Replace paths and the verified OCI digest before use; install a compatible Cosign version on your own release host.
    

    Warning · Image signatures, disk signatures and Secure Boot are different
    cosign verify checks an OCI release now; it does not configure bootc pull enforcement. A disk signature authenticates those exact file bytes, not its kernel or bootloader. A checksum alone proves neither authorship nor authenticity. Secure Boot needs its own supported boot-component signing and trust enrollment.
    

    Published OCI image · sign and verify by digest
    After publishing the tested image, sign its verified immutable digest. Signing requires registry access to publish signature material. Do not distribute the private key. Obtain the verification key through a trusted channel, not just alongside an untrusted image.

    bootc enforcement · configure and test host trust separately
    bootc uses the containers/image trust policy at /etc/containers/policy.json. Generic upstream defaults may permit unsigned images. A successful standalone Cosign check is not an enforced policy for future installs, switches or upgrades.
    Configure a reviewed, repository-scoped sigstoreSigned policy with your trusted public key and a matching signed identity, plus the required registry signature-discovery configuration. Preserve existing trusted vendor policies; do not blindly replace the global policy. Current Cosign uses OCI 1.1 referrers, while containers/image deployments may require use-sigstore-attachments and a different signature-storage convention. Check your exact RHEL, bootc, containers/image, registry and Cosign versions for interoperability before choosing the signing workflow.
    Current upstream documents bootc switch --enforce-container-sigpolicy; release availability and semantics must be checked on the installed host. Do not assume one flag or an external Cosign verification makes every future pull enforce signatures. On a disposable target, prove that your intended signed release succeeds and unsigned, wrong-key and wrong-repository candidates are rejected before rollout.

Recipients verify the bundle with an independently trusted public key before import or writing any target. A checksum is an additional integrity check, not a substitute for signature verification.     Before your first run
      Warning · Trusted builds only
      Do not run untrusted pull-request recipes on an entitled runner: build commands can access its resources and credentials. Use your provider's secret store, not recipe fields, uploaded files or source control.
      Runner and credential safeguards
      Use a disposable or dedicated runner with Bash, Podman and RHEL package entitlement. Restrict access to trusted, protected branches; scope tokens, protect environments, isolate workloads and rotate credentials. Use masked/protected secret variables where supported.
      The pipeline's private temporary registry-auth file is cleaned up on exit, but does not sandbox a build. Keep secrets out of logs, exported recipes and build context. Credential filters are incomplete; provision runtime secrets on the installed host, outside the image.
      Review→Build→Boot-test→Sign→Publish
      Info · Build and publish only
      These starters do not add boot tests, scanning, signing or protected promotion. YAML validation is not proof of runner execution, entitlement or bootability.
      Before production: delivery gates
      1. Build from reviewed source and pin production dependencies.
      2. Scan the image and retain its SBOM.
      3. Boot a disposable VM and verify your enabled services.
      4. Test upgrade and rollback, including application compatibility.
      5. Sign and publish an immutable image version.
      6. Promote to staging, then roll out through controlled production rings.
      These starters have not been validated by actual supported-provider runner runs. Test each provider independently on its specified runner; retain run links, tool versions, image digests and redacted build/boot logs. Commit-and-run tags avoid overwriting latest; enable registry immutability for enforced immutable releases.
